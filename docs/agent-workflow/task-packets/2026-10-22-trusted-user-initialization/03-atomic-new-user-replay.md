# Task Packet: atomic new-user initialization and historical replay

## Goal

One explicit service call creates a genuinely new active account, exact empty History and Memory snapshots, both real empty vector publication receipts, an RAG History witness, and one immutable schema17 completion credential in **one PostgreSQL transaction**. Repeating the saved operation UUID proves and returns the committed result through PostgreSQL alone, even if current S3/Qdrant is down or normal imports have advanced the user's current heads and snapshots.

This is a **draft for independent review**, not implementation or test execution authorization. Task01 and Task02 are accepted and scoped-delivered through base commit above. Root recorded Task02 remote-ref equality and delivery receipt SHA256 `93d1510b12fb5a00a396ed793d11e4c0879ea11213f2a06d85615b9849671008`. Root may then issue a tests-only writing GO; the resulting tests must be separately reviewed and frozen before the real RED execution GO. ## Delivery context

Task01 delivered resource-only settings and the schema17 immutable completion ledger. Task02 delivered a narrow private caller-cursor vector pair; its accepted focus34/regression80 evidence validates pair behavior, not user creation. An empty vector head has `generation_id=NULL` but `last_generation_id` points to a real published zero-count receipt. A missing head, missing snapshot, or historical account with no rows is never a trusted empty account. Schema17's before-insert guard checks that the account and complete baseline exist together before permitting a completion credential. The service must establish new-account provenance by its own same-transaction `INSERT users`, then call the Task02 pair on that cursor.

Historical replay authenticates the **current** active account with `verify_password` against its current `users.password_hash` (`docs/superpowers/specs/2026-10-22-trusted-user-initialization-design.md:72`). An old password fails after the account changes password; the valid current password may authenticate a replay. “Different password refuses” means one that fails current-account verification. Schema17 intentionally stores no original password verifier or plaintext. Replaying never rehashes or changes the password.

## Interface contract

### Consumes

- Caller-saved canonical `operation_id: UUID`; validated username/password and `TrustedUserInitializationSettings` with exact head17 schema. The service receives no `user_id`, trusted allowlist or mutable account target. Accept only the trusted original `PostgresDatabase`/real `ConnectionPool` construction above: its readable `_pool.conninfo` must have the same Task01 `_dsn` identity as `resources.database_url`, and its actual connection-acquisition timeout must be a readable, finite, non-bool number greater than zero and at most 10 seconds. A different or unattestable pool/identity, or an unbounded, absent or invalid timeout, is `configuration` before any proof/write. Do not create a generic pool wrapper or change `PostgresDatabase`.
- An external **read-only**, lazy `preflight()` callback. Invoke it exactly once only on a missing-operation new path, after initial PG lookup and before the PG write transaction. Task04 later implements actual S3/Qdrant checks. The callback must never run inside the write transaction or on completed replay.
- Exact Task02 pair method, caller-cursor snapshots, live lease and witness methods listed above. A user ID is generated with `uuid4()` by this service, not recovered from a missing snapshot.

### Produces

- Fresh success: one new active account and all five baseline components plus immutable ledger in one committed PG transaction; result has `durable_initialized=True,replayed=False` after independent operation-ID proof. If a commit response is lost but the ledger's `user_id` equals this invocation's generated candidate ID, confirmed proof still returns `replayed=False`; a proven competing winner with a different candidate returns `replayed=True`.
- Replay: same user and operation, `replayed=True` after current-account authentication and full historical proof. It performs no hash creation, preflight, lease acquisition, snapshot/head mutation or ordinary-data cleanup. If ordinary use has advanced heads/snapshots, the two original receipt IDs (state `published` **or** `retired`) and original immutable witness remain the proof.
- Known failure: raise the fixed code-only `InitializationError`; never return a failure dict or partial `InitializedUser`. Unknown commit/rollback: raise `InitializationOutcomeUnknown` with only the saved operation UUID/code, no new operation or automatic retry.

### Fixed error-code contract

| Code | Exact boundary |
| --- | --- |
| `invalid_request` | Noncanonical operation UUID or invalid username/password input, before any write. |

| `preflight_failed` | Missing-operation read-only external callback fails before PG write; no raw provider exception. |
| `conflict` | Existing username belongs to another operation, or known named unique conflict has no exact same-operation winner after one proof. |
| `mismatch` | Operation exists but request's username/resource/profile/scope binding, current active account status, or current password fails; never repair. |
| `corrupt` | Operation exists but immutable ledger or required historical receipt/witness/digest evidence is malformed, missing or inconsistent. |
| `busy` | Confirmed-rollback body lock timeout `55P03` or a provably unavailable lease on the new user. |

### Explicit transaction-outcome state machine (required for review)

Keep the existing `PostgresDatabase.transaction()` for this one write. For each invocation create one private, code-only `body_failed` sentinel **instance**, a local `entered` flag, and a local variable for the original body exception. Set `entered=True` immediately after `as cursor` enters. Inside the with-body, catch a body exception, save it privately, and `raise body_failed from None`; do not catch errors from the context manager's exit inside that body handler. After the **entire** context manager (including rollback, cursor close and pool exit) unwinds, classify a precommit rollback as confirmed **only** if the escaped exception `is body_failed`. That identity means the wrapper completed its rollback/cleanup without replacing the sentinel. Then and only then map the saved original error to named unique/busy/expired/timeout; neither its SQLSTATE nor its `__context__` alone proves abort. If acquisition failed with `entered=False`, no initializer body wrote anything: raise `unavailable` without an automatic outcome proof.

If the body completed normally but the context manager exits with an exception, commit **or cleanup** failed and rollback/cleanup completion is not proven; classify it as **unconfirmed**, even if the wrapper attempted a rollback. Do not label every such case “lost commit response.” If the body raised the sentinel but a different exception escapes, rollback or cleanup obscured confirmation and is also **unconfirmed**. In either case perform at most one bounded independent `REPEATABLE READ READ ONLY` operation-ID proof, with the same actual client-endpoint check and local 5/10/15-second timeouts. Exact committed proof returns durable success; absent, mismatched, pool-acquisition timeout, blocked proof query, unavailable, or inconclusive proof returns `unknown` with the saved operation UUID, without a second write. A normal context-manager return establishes successful commit; still perform the required independent postcommit proof, whose failure is `unavailable` because commit is confirmed. A deferred constraint or serialization error raised during commit is an exit failure under this conservative rule; do not infer known rollback from `23514`/`40001` or any other SQLSTATE alone. Real PG row checks must establish that such rejected transactions leave no partial baseline.

Tests must instrument the actual `database.transaction()` wrapper and exception identity. Inject a body `55P03` or named unique with normal rollback/cleanup and assert the same sentinel escapes, giving known classification with respectively zero or one **additional post-abort** proof. Inject rollback failure or cursor/pool cleanup replacement and assert a different escaped exception causes bounded proof/`unknown`. Inject commit-response loss after actual commit and require independent readback success; a commit-stage error with no durable row remains `unknown` unless a separately reviewed precise rule proves otherwise. With real PG, hold an exclusive lock on the ledger table across the initial proof and establish that the configured proof lock timeout produces sanitized `unavailable` before preflight/write; repeat the blocked proof after an ambiguous write exit and establish `unknown` with the original operation ID and no second write. Independently test pool-acquisition failure, finite-timeout rejection, endpoint mismatch and Task01 loopback host normalization. Real PG tests independently read committed rows after injected boundaries rather than trusting the return object alone. Never re-raise/log the original raw SQL/DSN exception.
