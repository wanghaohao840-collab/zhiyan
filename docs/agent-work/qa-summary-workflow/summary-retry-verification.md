# 失败摘要重试验收

失败摘要通过 `POST /api/v1/qa/messages/{message_id}/summary-retry` 重新进入后台队列。接口返回 `202` 和任务编号，页面可继续查询进度。新任务使用原指令和原会话固定的文档范围，保留失败消息。消息、重试关系和任务在一个 SQLite 事务内保存。重复点击同一失败消息返回同一任务。已被其他消息使用的请求编号会被拒绝。

模型只生成了半截摘要时，后台将该轮任务标记为 `QA_SUMMARY_INCOMPLETE`。首次失败可由用户手动重试一次。页面在已有重试或不符合重试条件时给出提示。普通问答沿用原重试入口，旧同步摘要重试的历史结果仍可由原入口取回。

## 本地验证

- 相关后端回归通过 113 项。最后一次修改请求编号校验和补充删除测试后，接口和数据库测试重新通过 44 项。覆盖同一消息并发重试、插入失败回滚、不同用户隔离、请求编号冲突、旧记录绑定、普通问答占用对话和删除隔离。
- 前端相关测试通过 32 项，`npm run build:app` 构建通过。Chromium 在 1440×1024 和 390×844 两种尺寸通过 4 项测试，实际点击了摘要重试、查看进度、取消等操作。浏览器使用临时 SQLite 和可控模型替身。
- GPT-6.2 Astra High 独立复核了事务、并发和历史数据兼容。Codex 修复复核发现的请求编号冲突，Astra 复核了修订。

## Neon 规划回执

基准 `33ccbf8`，模型 `gemini-4-neon-high`，会话 `cc4bc3d2-7848-4de9-83ae-bec9b1b3d4ce`。隔离规划目录内两次 `read_file` 调用成功，最终返回 `SUCCESS`。

Neon 比较了复用普通重试入口和增加摘要重试入口。选用独立入口返回 `QaJob`，使任务即刻结束时仍能拿到编号。由于 `qa_jobs` 的用户与输入消息组合必须唯一，任务包要求复制原指令到新输入，在同一事务内建立重试关系和后台任务，并用旧记录的请求绑定判断能否重放历史结果。验收覆盖后台实际入队、重复请求、删除保护、一次手动重试上限和页面状态恢复。Codex 另外覆盖了已有重试任务时复用其他消息请求编号的情况。
